先给 Cordis 画个像一句话认识它

Cordis 是一个「框架的框架」，它只干一件事：让软件里的模块能「带电拔插」——运行时想装就装、想拔就拔、想换就换，而且拔掉之后不留任何痕迹。

它跟你最近在聊的东西是什么关系？

🤖 DeepSeek Harness（DSH）用 Cordis 当地基建起来的 AI 助手平台插在插座板上的家电全家桶

你在 DSH 里见到的「插件」（plugin），就是 Cordis 世界里叫「组件」的东西。一句话：Cordis 是 DSH 的插线板，插件是插头，DSH 是整套电器。

1

为什么需要它？现在的软件有多「僵硬」痛点

痛点一：卸载个插件，居然要重启整个软件

拿 VSCode 举例。论文作者查了它家应用商店：装机量前 100 的插件里，87 个带可执行代码。你想卸载其中任何一个？对不起，得重启整个编辑器。

为什么？因为插件运行时会「搞脏」环境——占内存、注册事件、改配置。这些改动没人记账，所以拔掉插件时没人知道怎么还原，只能整台机器断电重启。

🏠 类比：请了个装修队，退租时才发现

装修队敲了墙、改了水管、拆了门。等你要退租，发现没有任何记录说明哪面墙原来是什么样。唯一的办法是整栋楼推倒重建（重启）——哪怕你只是想赶走一个工人。

痛点二：AI 要「自我进化」，但每次进化都要死机

这是论文真正的动机。未来的 AI 助手要能自己修改自己的组件：自己写个新工具、自己换个模块，而且 7×24 小时不中断地服务你。

如果每次自我修改都要重启：正在干的活被掐断、缓存全丢、用户全被踢下线。更糟的是——如果 AI 把自己改坏了，负责「修复」的那个进程也被它一起弄死了，那就彻底救不回来了。

现在的土办法：重启进程、重启容器

工业界的现状是「粗粒度妥协」：操作系统能管到「进程」这一层，Kubernetes 能管到「容器」这一层。要复原？重启。代价是：

  • 所有缓存、连接、内存里的状态全部丢掉，重建要几秒到几分钟
  • 想不断服务？得养双份备份，浪费资源
  • 它管不到进程内部——一个进程里 50 个模块，1 个坏了，得把 50 个全杀掉

Cordis 要做的就是把「管到单个模块」这件事变成可能：哪个模块坏了，就只换哪个。

2

两个核心魔法原理的心脏

魔法一（管「时间」）：可逆效应 —— 每个动作自带「撤销键」

规则很简单：插件做的每一个动作，都必须同时给出「怎么撤销」。

  • 占了一块内存 → 附上「怎么释放」
  • 注册了一个事件监听 → 附上「怎么注销」
  • 改了一个配置 → 附上「怎么改回去」

框架拿着这些撤销键自动记账，按「后做的先撤」的顺序串成一串。插件被拔掉的那一刻，框架从最后一步开始倒着按撤销键——系统就回到了插件装进来之前的样子。插件作者完全不用写「卸载清理代码」，因为清理是框架的自动功能。

🧅 类比：剥洋葱

后做的动作总是依赖先做的动作留下的状态，所以必须倒着撤，像剥洋葱从外往里。框架保证：不管插件干了几千件事，卸载时逐层剥干净，一片不剩。

魔法二（管「空间」）：响应式余效应 —— 依赖自己会「通电断电」

插件之间要互相用对方的能力。传统做法是「我直接用，没有就报错」。Cordis 的做法是声明式：

  • 插件在「身份证」上写明：我需要一个数据库、我需要文件系统……
  • 框架盯着这些声明。数据库一上线 → 依赖它的插件自动激活开工
  • 数据库一下线 → 插件自动停用，并且它干活期间产生的痕迹一并被撤销（魔法一登场）
🛵 类比：外卖平台的调度系统

骑手（插件）在平台上登记「我能接 A 区的单」（依赖声明）。平台（框架）看到 A 区有单了就派给他（激活），A 区没单了他就休息（停用）。骑手不用自己盯着地图看——调度是平台的自动功能。

两个魔法合起来 = 「时空可组合性」

论文标题里那个吓人的词，翻译成人话就是：

  • 时间上（temporal）：装上→干活→拔掉，时间轴上的每个点都是干净的
  • 空间上（spatial）：一堆插件同时在场时，谁依赖谁、谁先动谁后动，井井有条
3

一切走「总账房」：ctx原理的实体

ctx 是什么：一个万能插座 + 一本总账

两个魔法需要一个实体来落地。这个实体叫 ctx（context，上下文）。论文里定义它是「当前状态 + 撤销记账本 + 依赖表」三合一。规则铁一样简单：

插件对环境的一切改动，都必须通过 ctx 进行。绕开 ctx 的改动 = 黑户，框架看不见，也就管不了。

ctx 的四个常用柜台

柜台你把它想成作用
ctx.effect()📒 记账窗口包住一个动作及其撤销键，框架自动记账
ctx.set()📦 寄存处「我提供一个服务」，别人能来取
ctx.get()🛒 取件处「我取一个服务」，没有就等着（不报错）
ctx.tools.register()🔘 装按钮给 AI 注册一个能调用的工具

看一眼真实形状（看不懂代码没关系，看注释）

// 插件要注册一个「事件监听」
ctx.effect(() => {
  // ① 干活：注册监听
  const 监听器 = 注册监听(...)

  // ② 同时交出「撤销键」
  return () => 注销监听(监听器)
})

// 就这。将来插件被拔掉时，框架会自动执行那个撤销键。

注意那个 return () => 注销监听(...)：这就是「撤销键」。普通程序里它根本不存在，而 Cordis 里它是强制要求——这正是它跟所有传统框架的分水岭。

⚠️ 一眼看懂装坏了的插件：如果一个插件干了事却从不在 ctx.effect 里干，那它就是个「黑户」——装上容易，拔掉就留一堆垃圾。Vibe Coding 时让 AI 检查的就是这个。
4

插件的「身份证」和它的一生组件生命周期

每个插件（组件）的身份证上写着三行字

论文里叫 (d, p, e)，翻译成人话：

行内容白话
① 我要什么inject: [...]「我需要数据库、文件系统、工具注册表……」
② 我提供什么用 ctx.set() 等「我能提供『记忆』服务，谁要谁来拿」
③ 我干什么apply() 里的代码真正的活，全部通过 ctx 干

行①对应魔法二（依赖声明），行③里用 ctx.effect 干的活对应魔法一（自动记账）。三行字凑齐，框架就能全自动管理它的一生。

它的一生：装上 → 干活 → 拔掉

  • 装上（激活）：框架检查「我要什么」都齐了吗？齐了才开工，不齐就安静等着，绝不报错
  • 干活：apply 里的代码跑起来，所有副作用被记账
  • 拔掉（停用）：框架倒序按撤销键，它干的每一件事都还原如初；同时，依赖它的其他插件也被通知「供货商走了」，该停的停

再强调一遍和传统世界的差别：拔掉之后的清理不是插件作者的责任，是框架的自动保证。 VSCode 里卸载插件要重启，Cordis 里卸载插件就是按个键的事——系统其他部分照常运行。

🏢 类比：公司员工 vs 临时工

传统插件像「签了终身合同的员工」——请神容易送神难，离职时没人知道他在办公室留下了多少东西。Cordis 插件像「带完整交接清单的临时工」——入职时登记（inject），干活时每一步都留了恢复原状的办法（ctx.effect），离职时照着清单还原，办公室像他没来过一样。

5

热替换 HMR：给行驶中的车换轮胎改代码不重启

HMR 是什么

HMR = Hot Module Replacement（热模块替换）。你在 Vibe Coding 时改了一个插件、改了配置文件，保存的瞬间就生效：旧的拔掉、新的装上，整个系统不停机。

🏎️ 类比：F1 进站换胎

赛车不停（进程不重启），换胎工（Cordis）卸下旧胎（撤销旧插件的全部副作用）、装上新胎（激活新插件），3 秒出站。乘客（正在运行的会话）全程没感觉。

更关键的是：换坏了会自动「回滚」

新代码有语法错误？新配置填错了？Cordis 的替换是事务性的，像银行的转账：

  • 要么全部换成新的（成功）
  • 要么全部退回旧的（失败自动回滚）
  • 绝不停在「换了一半」的半吊子状态

换到第 5 个插件时失败了？前 4 个已经换掉的会被自动撤回来，系统跟你保存前一模一样，然后报个错告诉你哪出问题了。这在传统系统里想都不敢想——重启失败就是崩溃现场。

为什么敢这么玩？因为魔法一兜底

能「回滚」的底气来自第 2 章：每个插件的每个动作都有撤销键。旧插件能完整退场、新插件随时能补位，才谈得上「热替换」。没有可逆效应，HMR 就是空中楼阁。

6

串起一切：Cordis、DSH、插件、tool、MCP全景图

它们不是并列关系，是四个层次

东西层次一句话
Cordis地基管「模块怎么带电拔插」的框架
插件架构单元一段被 Cordis 全权管理的代码，是「员工」
tool能力单位AI 能按的按钮，是插件注册出来的「技能」
MCP通信协议把外部程序（外包团队）的工具运进 DSH 的「管道」

三个好记的类比

  • 插件 = 员工：公司（Cordis）管他入职、干活、离职全流程。员工不仅能提供技能（tool），还能提供内部服务（ctx.set）给别的员工用。
  • tool = 技能：员工掌握的某个按钮。一个员工可以会 0 个、1 个、100 个技能。
  • MCP server = 外包团队：不是公司员工，是外部程序。公司派一个对接人（dsh-mcp-client 桥接插件）跟他们用协议（MCP）沟通，借来的技能照样注册进技能表。

所以之前聊的结论在这里汇合：MCP 不是一堆 tool，MCP 是协议；「一堆 tool」的是 MCP 服务器；tool 跑在你本机，不跑在云端；云端只有模型的大脑。

为什么 DSH 选 Cordis 当地基？

回到论文的动机：未来的 AI 助手要自己给自己装插件、改插件、换插件，全程不间断。这要求地基必须做到三件事，而 Cordis 恰好全有：

  • ✅ 拔掉不留痕（可逆效应）—— AI 试验新插件，试坏了随时撤
  • ✅ 依赖自动启停（响应式余效应）—— AI 换了个数据库驱动，只有相关插件重启，别的无感
  • ✅ 改代码不重启 + 失败自动回滚（HMR）—— AI 自我迭代的节奏才跟得上

DSH 的口号「Everything is a Plugin（一切皆插件）」，就是 Cordis 理念的落地宣言。

7

Vibe Coding 实操：你只需要会这几个姿势会用就行

姿势一：装插件 = 改一份「装机清单」

DSH 里所有插件都在一个叫 cordis.yml 的文件里登记。你想给 AI 加什么能力，就往清单里加一行：

# 给 AI 接上 GitHub 的 MCP 工具包（每个服务器 = 一个插件实例）
- id: mcp-github
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: github
    transport: stdio
    command: npx
    args: ['-y', '@modelcontextprotocol/server-github']
    env:
      GITHUB_TOKEN: !!js process.env.GITHUB_TOKEN

改完保存，不用重启——HMR 自动生效（第 5 章），AI 立刻多了一批 mcp__github__* 工具。这就是最常见的日常操作。

姿势二：写新插件 = 让 AI「照葫芦画瓢」

要写自己的插件时，最稳的姿势是：

  1. 在 DSH 源码的 packages/ 目录里找一个功能相近的现成插件
  2. 复制它，改名字、改 inject（我要什么）、改 apply（干什么）
  3. 让 AI 照着改，并明确要求：所有副作用都必须包在 ctx.effect 里

千万不要让 AI 从零发明架构——Cordis 的规矩就那几条，照官方例子改是零风险路径。

姿势三：三句「咒语」，验收 AI 写的插件

拿到 AI 写的插件代码，你只需要问三个问题（也用来命令 AI 自查）：

  • ① 它的副作用都在 ctx.effect 里吗？——不在就是「黑户」，拔掉留垃圾
  • ② 它要的东西都写进 inject 了吗？——没写就是「偷偷伸手」，依赖没了它会崩
  • ③ 拔掉再装上，系统能复原吗？——这就是 Cordis 的验收标准，也是你作为产品负责人唯一需要关心的指标
💡 给 Vibe Coder 的总纲：在 Cordis 世界里，你不需要懂「怎么清理」，因为框架包了；你只需要监督一件事——AI 有没有绕开 ctx 乱来。绕开 ctx 的代码，等于在带保险的插座板上私拉电线。
